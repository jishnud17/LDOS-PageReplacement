SIGNAL GLOSSARY (what each metric measures, in access-rate terms)
-----------------------------------------------------------------
Every signal is computed per page over a rolling window of access-rate bars
(one bar per sampling interval; nominally 50ms).

  random_walk_index_high   How far the access rate actually moved over N bars
                           vs. what a random walk would produce.  High value =
                           trending, not noise.
  random_walk_index_low    Same, over a shorter lookback.
  swing_index              Size of the current bar's rate move relative to the
                           bar's total range ("how decisive was this step").
  accum_swing_index        Running cumulative sum of swing_index.
  schaff_trend_cycle       Cycle detector on double-smoothed moving averages;
                           0-100 oscillator.  Confirms trends; inherently lags.
  parabolic_sar            Trailing stop level that accelerates with a trend.
  parabolic_sar_direction  +1/-1: which side of the SAR the rate is on.
  range_action_verification_index (RAVI)
                           Short moving average vs. long moving average, in
                           percent; momentum vs. trend.
  avg_directional_index    Trend strength regardless of direction.
  aroon_down / aroon_up    Bars since the window's minimum / maximum rate.
  interval_access_rate     The raw per-bar access rate itself (not an
                           indicator; the underlying series).
  inter_access_interval_ms Mean time gap between consecutive accesses.
  system_quality_number    Mean rate-change divided by std of rate-changes.
  ichimoku_* family        Moving-average midpoints over 9/26/52-bar windows.
                           NOTE: ichimoku_chikou duplicates interval_access_
                           rate in our implementation -- excluded from ranks.
  linear_reg_slope /       Least-squares line fit over the lookback window.
    intercept
  recency_weighted_frequency  Access rate with exponential decay favoring
                           recent accesses.

WHAT WAS RUN
------------
All workloads under identical collection: telemetry-only mode (LD_PRELOAD
shim intercepts the application's large allocations; pages fault natively;
access data comes exclusively from PEBS hardware sampling on per-CPU events
covering all threads; no migrations).  Overhead: zero measurable (GUPS
throughput identical with and without the manager attached).

  A. hot_cold synthetic (graded hot/warm/cold split) under telemetry mode.
     410 hot pages tracked, 52K rows.
     Events: 413 hot_to_cold, 17 cold_to_hot.
     Signal cadence: held at ~50ms bars (clean).

  B. GUPS hotset-move (gups_hemem from the provided workloads repo; the
     HeMem benchmark).  90/10 skewed random updates over a 2GB table; the
     hot set RELOCATES mid-run -- a real hot-set migration.
     2.49M rows, 159K pages observed.
     Events: 83 hot_to_cold, 52 cold_to_hot (41 / 18 with full windows).
     Signal cadence: STRETCHED to ~1.5s bars (159K tracked pages overloaded
     the 50ms signal loop) -- see caveat under B's rankings.

  C. GUPS skewed (static hot set): run completed too quickly (3s) to
     accumulate enough bars per page for event analysis.  No rankings.

  D. GAPBS PageRank / Twitter graph: integrated and executed end-to-end,
     but produced no load telemetry due to a hardware defect on this node
     family (see PEBS HARDWARE FINDING).

     dead in this dataset (amplitudes 0.01-0.04).
  5. Slow smoothers (Ichimoku, VHF, GAPO) are dead weight at 50ms cadence.

  4. inter_access_interval_ms is dead here as well.

================================================================================
PEBS HARDWARE FINDING (affects what this node family can measure)
================================================================================

On the CloudLab c220g2/g5 (Haswell-generation) nodes, PEBS LOAD sampling
counts events correctly but reports a garbage constant data address
(0xfeb8xxxx) for virtually all load samples.  STORE address capture is
correct.  Verified independently with stock `perf mem` (kernel reference
tooling, our code not involved), and cross-checked against three event
encodings.

Consequences:
  - All telemetry in this round is store-driven.  Write-bearing workloads
    (GUPS updates, synthetic hot pages) attribute perfectly; read-only
    regions (PageRank's graph arrays) are invisible.
  - GAPBS PageRank / Twitter requires a Skylake-class node (e.g. CloudLab
    c6420) -- the hardware class MEMTIS and HeMem target.
  - Secondary finding: a dense single-address store stream (a debug sink
    written every loop iteration) absorbed store attribution from
    neighboring stores (612K samples -> 64 pages; removing it restored
    410/410 hot pages).  Transparent Huge Pages were ruled out by direct
    experiment.

LIMITATIONS
================================================================================

1. GUPS rankings are cadence-distorted (see B's caveat).  Clean rankings
   need the tracked-page bound first.
2. gups-skewed run too short for analysis; rerun is cheap when node time
   permits (hotset-move covers the same pattern plus the transition).
3. cold_to_hot samples are small (n=17-18): pages with no write activity
   produce no samples on this node family, so pages first appear in the
   data near their warm-up.
4. Single run per configuration; no replication yet.
