SIGNAL GLOSSARY (what each metric measures, in access-rate terms)
-----------------------------------------------------------------
Every signal is computed per page over a rolling window of access-rate bars
(one bar per 50ms sampling interval).

  random_walk_index_high   Compares how far the access rate actually moved
                           over N bars vs. what a random walk would produce.
                           High value = the rate is trending, not noise.
  random_walk_index_low    Same, over a shorter lookback; catches shorter
                           trends.
  swing_index              Size of the current bar's rate move relative to
                           the bar's total range; "how decisive was this step."
  accum_swing_index        Running cumulative sum of swing_index.
  schaff_trend_cycle       Cycle detector built on double-smoothed moving
                           averages; 0-100 oscillator, extremes = trend
                           established.  Confirms trends; inherently lags.
  parabolic_sar            Trailing stop level that accelerates as a trend
                           extends (raw level).
  parabolic_sar_direction  +1/-1 flag: which side of the SAR the rate is on;
                           flips when the trend reverses.
  range_action_verification_index (RAVI)
                           Short-period moving average vs. long-period moving
                           average, as a percent difference; momentum vs trend.
  avg_directional_index    Trend strength regardless of direction (smoothed
                           |+DI - -DI| / (+DI + -DI)).
  interval_access_rate     The raw per-bar access rate itself (accesses/sec
                           measured in the last bar).  Not an indicator --
                           the underlying series.
  inter_access_interval_ms Mean time gap between consecutive accesses to the
                           page.  Shrinks before a page heats up -- phase-1's
                           only LEADING signal.
  system_quality_number    Mean rate-change divided by std of rate-changes;
                           trend quality.
  ichimoku_* family        Moving-average midpoints over 9/26/52-bar windows
                           (tenkan/kijun/senkou_a/senkou_b/chikou).  NOTE:
                           ichimoku_chikou duplicates interval_access_rate in
                           our implementation (known artifact) -- excluded
                           from rankings.
  linear_reg_slope/intercept  Least-squares line fit over the lookback window.
  recency_weighted_frequency  Access rate with exponential decay favoring
                           recent accesses.

WHAT WAS RUN
------------
All real workloads come from the mentor-provided repositories:

  1. GUPS (gups_hemem, from SujayYadalam94/workloads) -- the HeMem benchmark.
     Two variants run under the tiered-memory manager in telemetry mode:
       - gups-hotset-move : 90/10 skewed updates, hot set relocates mid-run
                            (2GB table, 128 hot pages, move at t=15s, 35s run)
       - gups-skewed      : static 90/10 hot set (run came out too short --
                            see LIMITATIONS)

  2. GAPBS PageRank on the Twitter graph (gapbs + memtis gen-twitter diff).
     Built, integrated, and executed end-to-end; blocked from producing load
     telemetry by a hardware defect on the CloudLab node family (see PEBS
     HARDWARE FINDING).  Queued for a Skylake-class node.

  3. Control: the phase-1 synthetic hot_cold workload re-run under the SAME
     collection method as the real workloads (PEBS telemetry-only mode).
     This isolates "did the measurement change?" from "did the workload
     change?" -- without it, any ranking difference between phase-1 and the
     real workloads would be confounded.

COLLECTION METHOD (what changed vs phase-1)
-------------------------------------------
Phase-1 used full management: userfaultfd demand paging + write-protect
fault counting + PEBS, on synthetic workloads compiled into the manager.

Real applications cannot pay the demand-paging cost (measured 2500x slowdown
on first touch), so real workloads run in TELEMETRY-ONLY mode:
  - LD_PRELOAD shim intercepts the application's large allocations
  - pages fault natively at full speed (zero measurable overhead:
    GUPS throughput identical with and without the manager attached)
  - access data comes exclusively from PEBS hardware sampling
  - per-CPU perf events with inheritance sample ALL application threads
  - no migrations occur (telemetry, not policy, is being evaluated)

================================================================================
RESULT 2: END-TO-END VALIDATION ON A REAL TIERED-MEMORY BENCHMARK
          (GUPS hotset-move)
================================================================================

2.49M rows, 159K pages observed, 83 hot_to_cold + 52 cold_to_hot events
detected from a REAL hot-set migration (the benchmark relocates its hot
region mid-run; the pipeline captured the transition).

  - Reactions are enormous and near-unanimous: 5-32 sigma amplitudes at
    0.89-1.00 consistency across events.
  - random_walk_index_high (trend-vs-noise detector): 7.3 sigma, consistency
    1.00, coincident -- the phase-1 top signal fires perfectly on a real
    workload's transitions.
  - avg_directional_index (direction-free trend strength): 9.6 sigma at
    consistency 1.00 on both event types.

IMPORTANT CAVEAT -- signal RANKING on this dataset is not comparable to
phase-1: the raw rate and slow smoothers (Ichimoku moving averages, linear
regression fits) rank at the top here, inverting phase-1.  Cause: the run
tracked 159K pages (GUPS's 10% uniform traffic touches the whole 2GB table),
which stretched the policy thread's 50ms signal cadence to ~1.5s per bar.
At 1.5s resolution, GUPS's transitions are single-bar cliffs -- every signal
fires on the same bar, and amplitude ordering reflects normalization rather
than reaction speed.  Fast-vs-slow signal discrimination requires holding
the 50ms cadence, which requires bounding the tracked-page count (an
identified, straightforward engineering fix: cold-page thinning).

TAKEAWAY: the telemetry pipeline works end-to-end on a real benchmark and
detects real transitions with the expected signals responding.  Clean
real-workload signal RANKINGS require the cadence fix first.

================================================================================
RESULT 3: THE LEADING SIGNAL REQUIRES PER-ACCESS TIMESTAMPS
          (methods finding)
================================================================================

Phase-1's most interesting signal -- inter_access_interval_ms, the mean time
gap between consecutive accesses to a page, and the only signal that LED
cold_to_hot transitions (by 100-250ms) -- collapsed in every telemetry-mode
dataset (amplitudes 0.01-0.35 vs phase-1 scores up to 3.2).

This is not a workload effect; it is a measurement-granularity effect.  In
phase-1, userfaultfd write-protect faults gave a truthful timestamp for
each access, and the interval signal measured real gaps between accesses.
In telemetry mode, access times are quantized to the 10ms PEBS merge
cadence, destroying the fine-grained gap structure the signal depends on.

IMPLICATION FOR PHASE-2: the predictive-lead property discovered in phase-1
is real but conditional on the tracking mechanism.  A deployed system that
wants the early-warning signal must either retain a UFFD-style per-access
timestamp path for candidate pages, or timestamp PEBS samples individually
at ingest (feasible: perf records carry timestamps; currently discarded at
merge).  The second option is the natural phase-2 engineering item.

================================================================================
PEBS HARDWARE FINDING (affects platform requirements)
================================================================================

On the CloudLab c220g2/g5 (Haswell-generation) nodes, PEBS LOAD sampling
counts events correctly but reports a garbage constant data address
(0xfeb8xxxx) for virtually all load samples.  STORE address capture is
correct.  Verified independently with stock `perf mem` (kernel reference
tooling, our code not involved): the same garbage data symbols dominate its
output.  Cross-checked against three event encodings (MEM_UOPS_RETIRED.
ALL_LOADS, the load-latency facility 0x1CD, and perf mem's own config).

Consequences:
  - All telemetry on this node family is store-driven.  Write-bearing
    workloads (GUPS updates, synthetic hot pages) attribute perfectly;
    read-only regions (PageRank's graph arrays) are invisible.
  - Phase-1 was immune by accident: its synthetic workloads write every
    hot page (1 write per 8 reads), so store samples carried the signal.
  - GAPBS PageRank/Twitter (mentor-provided) is integrated and runs
    end-to-end but needs a Skylake-class node (e.g. CloudLab c6420) for
    load telemetry -- the same hardware class MEMTIS and HeMem target.

Two secondary attribution effects were found and fixed along the way:
  - A dense single-address store stream (a debug sink variable written
    every loop iteration) absorbed store-sample attribution from
    neighboring region stores (612K samples -> 64 pages before the fix;
    410/410 hot pages after).  Lesson: PEBS attribution is sensitive to
    interleaved high-frequency store streams.
  - Transparent Huge Pages were ruled out as a cause by direct experiment
    (THP=never changed nothing).

LIMITATIONS (stated plainly)
================================================================================

1. gups-skewed produced too few signal bars (the concentrated hot set made
   the fixed update count finish in 3s; series shorter than the event
   detector's minimum).  Rerun with a larger update count when node time
   permits.  gups-hotset-move covers the same access pattern plus the
   transition, so the loss is redundancy, not coverage.

2. GUPS ranking comparability is limited by the bar-cadence stretch
   (RESULT 2).  Fixing it is engineering, not research risk.

3. cold_to_hot event counts are small in telemetry mode (n=17-18): pages
   with no write activity produce no samples, so pages first appear in the
   data near their warm-up.  Store-side limitation of this node family.

4. Single run per configuration; no replication yet.
